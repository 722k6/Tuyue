# 途越项目六人分工实施方案

> 本方案依据《需求梳理说明》《途越官网与后台管理系统 PRD》《用户故事》《开发规范》编制。由于目前没有六位成员的个人技能画像，姓名与岗位的对应关系采用“角色先行”的默认分配；若成员实际能力不匹配，只交换姓名，不改变六条责任线、接口边界和验收责任。

## 一 结论

六人团队不建议平均切页面，也不建议简单分为三名前端和三名后端。项目同时包含官网、CMS、结构化车型数据、在线选配、AI 流式对话、权限、统计与地图，最容易失败的地方是接口口径不一致和模块之间无人负责。建议采用“一个技术负责人加五个业务域负责人”的模式：

| 成员 | 主责任线 | 主要交付 | 次责任 |
|---|---|---|---|
| 林涛 | 技术负责人及后端基础平台 | 工程骨架、数据模型、鉴权与权限、公共 API、部署基线 | 后端代码总评审、接口仲裁 |
| 唐轩 | 访客端官网及车型展示 | 首页、车型列表、车型详情、响应式、前端公共组件 | 官网性能和可访问性 |
| 汤毅威 | CMS 管理端 | 登录、角色界面、车型活动经销商 CRUD、审核发布 | CMS 易用性和表单校验 |
| 糜昊廷 | AI 选车全栈 | 流式对话、车型上下文、推荐结果、护栏、AI 评测 | AI 成本与质量监控 |
| 李昱彤 | 购车决策工具 | 车型对比、差异高亮、在线选配、计价引擎 | 跨页面选车状态 |
| 周子涵 | 运营能力及质量发布 | 活动、经销商地图、数据看板、埋点、E2E、CI 发布 | 测试负责人和版本验收 |

工作量目标不是让六个人写相同代码量，而是让每个人拥有一条能独立演示、独立测试、独立验收的交付链路。

## 二 一期范围与明确不做事项

### 必须完成

- 车型后台 CRUD、上下架、排序和前台列表详情。
- 编辑、审核、超管三种固定角色的登录和权限控制。
- AI 选车对话、推荐理由、追问、推荐卡片跳转。
- 最多四款车型对比和差异高亮。
- 在线选配、价格实时汇总。
- 活动、经销商、数据看板。
- 主流浏览器与移动端响应式。

### 本期不做

- 新闻资讯。
- 试驾预约、询价留资和线索后台。
- 在线购车及支付。
- 自定义细粒度权限。
- 英文内容录入；只预留国际化结构。

任何人不得在开发过程中把这些延期项顺手加入一期。

## 三 推荐技术架构

### 统一技术栈

| 层次 | 推荐技术 | 采用原因 |
|---|---|---|
| 仓库 | pnpm workspace monorepo | 官网、CMS、API 和共享类型统一版本与联调 |
| 官网 | Vue 3、TypeScript、Vite、Vue Router、Pinia、SCSS | 与 PRD 指定的 Vue 一致，适合响应式官网和状态共享 |
| CMS | Vue 3、TypeScript、Vite、Element Plus、Pinia | 表格、表单、上传、弹窗等管理端组件成熟 |
| API | Node.js、NestJS、TypeScript、REST、OpenAPI | 模块边界清晰，适合六人并行和自动生成接口文档 |
| 数据库 | PostgreSQL、稳定版 Prisma ORM | 车型、配置、活动、经销商、权限和统计均为关系型数据 |
| 文件 | 开发环境 MinIO，生产环境对象存储适配器 | 统一处理车型图、活动封面和门店图片 |
| AI | Anthropic TypeScript SDK、Messages API、SSE | API 密钥只在后端；流式内容由后端转发给官网 |
| 地图 | `MapProvider` 适配层 | 高德、腾讯、百度尚未确定，先隔离供应商实现 |
| 测试 | Vitest、Vue Test Utils、Nest 测试工具、Supertest、Playwright | 覆盖单元、接口、组件和端到端主流程 |
| 工程质量 | ESLint、Prettier、commitlint、husky、lint-staged | 六人统一格式与提交门禁 |
| CI CD | GitHub Actions、Docker、Nginx | PR 自动校验，测试环境统一部署 |

### 版本原则

- 初始化时锁定 Node LTS、pnpm、Vue、NestJS、数据库和 ORM 的具体版本，并提交 lockfile。
- 生产环境只使用稳定版依赖，不在主链路采用 RC 或 Preview。
- Claude 模型名写入环境配置 `ANTHROPIC_MODEL`，业务代码不得硬编码模型标识。
- 地图供应商、AI 预算和数据留存策略确认前，使用适配接口和可替换配置，不阻塞其他模块。

### 建议目录

```text
Tuyue/
├─ apps/
│  ├─ web/                  # 访客官网
│  ├─ admin/                # CMS 管理端
│  └─ api/                  # NestJS API
├─ packages/
│  ├─ contracts/            # DTO、枚举、OpenAPI 生成类型
│  ├─ ui/                   # 官网可复用基础组件和设计 token
│  ├─ config/               # ESLint、TypeScript、环境配置
│  └─ test-utils/           # mock、fixture、测试数据工厂
├─ e2e/                     # Playwright 端到端测试
├─ docs/
│  ├─ api/                  # 接口及错误码约定
│  ├─ adr/                  # 架构决策记录
│  └─ test/                 # 测试计划和验收记录
└─ infra/                   # Docker、Nginx、CI 配置
```

## 四 六人详细分工

### 1 林涛 技术负责人及后端基础平台

#### 负责板块

- 建立 monorepo、三个应用、共享包、环境变量模板和本地启动脚本。
- 设计 PostgreSQL 数据模型，建立 Car、CarConfig、Activity、Dealer、Admin、Role、AiConversation、AnalyticsEvent 等实体。
- 实现管理员登录、JWT、密码哈希、三种固定角色、路由权限守卫。
- 建立图片上传抽象、对象存储适配、软删除、审计字段、统一异常和日志。
- 输出 OpenAPI，维护接口版本、错误码、分页格式和 DTO 规范。
- 维护 Docker、测试环境、数据库迁移和发布回滚基线。
- 仲裁跨模块数据字段和接口变更；审批所有数据库迁移。

#### 技术栈

NestJS、TypeScript、PostgreSQL、Prisma ORM、JWT、Argon2、OpenAPI、Docker、Nginx、GitHub Actions。

#### 核心交付物

- `apps/api` 可启动并通过健康检查。
- 管理员可登录，未登录请求被拒绝，三种角色拥有正确权限。
- 数据库迁移可从空库重复执行。
- Swagger 或 OpenAPI JSON 可供前端生成类型。
- `.env.example` 不包含任何真实密钥。

#### 验收标准

- 编辑只能新增编辑并提交审核，不能直接发布。
- 审核可发布和下线，不能管理账号。
- 超管拥有全部权限并可维护账号角色。
- 接口错误统一返回 `code`、`message`、`requestId`。
- 关键接口具备单元测试和 Supertest 集成测试。

#### 边界

林涛不包揽全部业务接口。业务域负责人先提交接口草案和测试，林涛负责公共规范、数据一致性和最终评审。

### 2 唐轩 访客端官网及车型展示

#### 负责板块

- 首页导航、品牌首屏、推荐车型、活动入口和 AI 入口。
- 车型列表、能源类型和价格筛选、加载态、空态和图片占位。
- 车型详情的大图轮播、价格、参数表、关联推荐。
- 移动端响应式、SEO 基础标签、页面性能和无障碍基础。
- 建立官网布局、路由、主题 token 和可复用展示组件。

#### 技术栈

Vue 3、TypeScript、Vite、Vue Router、Pinia、SCSS、Axios 或基于 OpenAPI 生成的 API Client、Vitest、Vue Test Utils。

#### 核心交付物

- `apps/web` 的首页、车型列表、车型详情三条完整用户路径。
- `CarCard`、`CarGallery`、`ParameterTable`、`EmptyState`、`LoadingSkeleton` 等公共组件。
- 车型数据全部来自 CMS API，不出现页面硬编码车型。
- 适配桌面、平板和手机三类视口。

#### 验收标准

- 车型列表和详情与 CMS 发布状态同步。
- 图片失败显示占位，接口失败显示可重试状态。
- 筛选条件可通过 URL 查询参数恢复。
- 首屏目标不超过 PRD 的三秒要求；在约定测试环境记录 Lighthouse 基线。

#### 协作接口

- 从林涛获得 Car DTO 和统一 API Client。
- 向李昱彤提供“加入对比”和“进入选配”的入口组件。
- 向糜昊廷提供 AI 推荐卡片复用的车型卡片样式与路由协议。

### 3 汤毅威 CMS 管理端

#### 负责板块

- CMS 登录页、主布局、菜单、路由守卫和角色可见性。
- 车型的新增、编辑、软删除、上下架、排序、图片和参数录入。
- 颜色、内饰、配置包的管理表单。
- 活动与经销商的 CRUD 管理界面。
- 编辑提交审核、审核发布和下线的状态流转界面。
- 账号和角色管理页面，仅对超管开放。

#### 技术栈

Vue 3、TypeScript、Vite、Element Plus、Pinia、Vue Router、VueUse、表单校验库、Vitest、Vue Test Utils。

#### 核心交付物

- `apps/admin` 的登录、工作台和各业务管理页面。
- 通用 `DataTable`、`SearchForm`、`ImageUploader`、`StatusTag`、`ReviewDialog`。
- 防止重复提交、未保存离开提醒、字段级错误提示。
- 权限不足时隐藏操作入口，同时正确处理后端 403。

#### 验收标准

- 新建或修改车型后必须按“草稿到待审核到已发布”流转。
- 保存后的已发布数据能在官网正确展示。
- 车型参数、价格、时间区间、经纬度等字段具备前后端双重校验。
- 表格查询、分页、筛选和刷新后状态保持正确。

#### 协作接口

- 与林涛共同定义权限码、审核状态机和上传协议。
- 与李昱彤共同定义配置项字段与价格规则。
- 与周子涵共同定义活动、经销商和地图坐标字段。

### 4 糜昊廷 AI 选车全栈

#### 负责板块

- AI 对话页面和全局浮窗，支持流式文本、停止、重试和追问。
- 后端 AI 模块、Anthropic SDK 封装、SSE 转发、超时和限流。
- 把已发布车型的结构化数据转换为受控上下文。
- 要求模型返回结构化推荐：车型 ID、推荐理由、匹配条件和缺口说明。
- 防止推荐不存在或未发布的车型，最终结果由服务端二次校验。
- 记录输入摘要、模型、用量、耗时、推荐车型和失败原因。
- 建立 AI 离线评测集，覆盖无匹配、超范围提问、诱导虚构参数和多轮追问。

#### 技术栈

Vue 3、TypeScript、NestJS、Anthropic TypeScript SDK、Messages API、SSE、JSON Schema 或结构化输出校验、Vitest、Supertest。

#### 核心交付物

- `POST /ai/conversations` 与流式消息接口。
- `AiRecommendation` 结构化结果，车型只用 `carId` 关联真实数据库。
- Prompt 模板、车型上下文构建器、输出验证器、成本统计。
- 至少 30 条固定 AI 评测用例和可重复执行的评测报告。

#### 验收标准

- 推荐车型必须存在、已发布并与 API 返回参数一致。
- 无匹配车型时明确说明，不生成虚假车型或参数。
- 推荐卡片可跳转详情和加入对比。
- 网络中断、模型超时、限流和内容为空都有明确 UI 状态。
- 密钥只存在服务端，浏览器请求中不得出现 Anthropic API Key。

#### 协作接口

- 从林涛获取已发布车型查询和统一日志能力。
- 复用唐轩的车型卡片和路由。
- 调用李昱彤的对比状态接口，不自行实现第二套对比列表。
- 向周子涵发送 AI 使用量、成功率和耗时事件。

### 5 李昱彤 购车决策工具

#### 负责板块

- 车型列表和详情页的“加入对比”，维护跨页面对比篮子。
- 最多四款车型、超限提示、一键清空和单项移除。
- 对比表参数对齐、缺失值展示和差异高亮。
- 在线选配器的颜色、内饰、配置包选择、预览图和价格实时汇总。
- 建立确定性的计价引擎，不能依赖前端显示值作为最终价格。
- 与 CMS 配置项管理打通。

#### 技术栈

Vue 3、TypeScript、Pinia、组合式 API、CSS Grid、NestJS 业务模块、Decimal 精确金额计算、Vitest、fast-check 可选属性测试。

#### 核心交付物

- `comparison` Pinia store 与持久化策略。
- `CompareTable`、`DifferenceHighlight`、`Configurator`、`PriceSummary`。
- 后端配置项读取和报价校验接口。
- 参数标准化字典，保证不同车型按同一字段顺序比较。

#### 验收标准

- 第五款加入时被阻止并提示原因。
- 同一车型不能重复加入。
- 缺失参数显示为“未提供”，不误判为差异或数值零。
- 配置互斥、必选、价格叠加和取消选择均有测试。
- 服务端重新计算的总价与前端展示一致，金额采用精确小数处理。

#### 协作接口

- 与汤毅威共同确定配置项表单和互斥规则。
- 与唐轩共同确定车型参数表和页面入口。
- 向周子涵发送对比次数和选配使用事件。

### 6 周子涵 运营能力及质量发布

#### 负责板块

- 官网活动列表和详情、首页 banner 数据接入。
- 经销商列表、详情、地图定位、电话和营业时间。
- 地图适配层的前端实现，在服务商未定时先提供 mock provider。
- 定义并接入浏览、车型点击、对比、AI、活动曝光等埋点。
- CMS 数据看板：总访问量、热门车型、AI 使用量、对比次数、活动曝光，支持时间筛选。
- 维护 Playwright 主流程、测试数据、GitHub Actions 质量门禁和版本验收清单。
- 组织缺陷分级、回归和发版检查，但各模块负责人仍负责修复自己的缺陷。

#### 技术栈

Vue 3、TypeScript、ECharts、地图 JavaScript SDK 适配器、NestJS Analytics 模块、PostgreSQL 聚合查询、Playwright、GitHub Actions、Docker。

#### 核心交付物

- 活动和经销商访客端页面。
- `MapProvider` 接口及至少一个 mock 实现。
- 统一 `track(eventName, payload)` 客户端接口和服务端事件表。
- 数据看板及统计口径说明。
- 覆盖登录、发布车型、前台浏览、AI 推荐、加入对比、在线选配的 E2E 套件。

#### 验收标准

- 地图按经纬度定位，供应商切换不影响业务页面接口。
- 数据看板每个指标有明确口径、时间区间和去重规则。
- 埋点失败不阻塞用户主流程。
- PR 必须通过 lint、typecheck、unit、API integration 和关键 E2E 后才可合并。
- 发布前不存在 S0 或 S1，S2 必须有处理结论。

#### 边界

周子涵是质量流程负责人，不是全队唯一测试人员。每个人为自己的模块编写单元和接口测试，周子涵维护跨模块 E2E 与发布门禁。

## 五 模块接口边界

### 共享契约优先

开发开始前先冻结第一版契约，至少包含：

- `CarSummary`、`CarDetail`、`CarParameter`、`CarConfigOption`。
- `PublishStatus`、`AdminRole`、`PermissionCode`。
- `CompareItem`、`CompareParameterRow`。
- `ConfigurationSelection`、`QuoteResult`。
- `AiChatRequest`、`AiStreamEvent`、`AiRecommendation`。
- `ActivityDto`、`DealerDto`、`AnalyticsEvent`、`DashboardMetrics`。
- 分页、错误响应、上传响应和时间格式。

共享类型放在 `packages/contracts`；任何破坏性变更必须先更新契约、OpenAPI 和相关测试，再通知受影响负责人。

### 数据所有权

| 数据或规则 | 第一责任人 | 必须评审人 |
|---|---|---|
| 数据库模式和迁移 | 林涛 | 对应业务负责人 |
| 车型展示字段 | 唐轩 | 林涛、汤毅威 |
| CMS 表单与审核状态 | 汤毅威 | 林涛 |
| AI Prompt 与推荐校验 | 糜昊廷 | 林涛、周子涵 |
| 对比字段与计价规则 | 李昱彤 | 唐轩、汤毅威 |
| 统计口径与埋点字典 | 周子涵 | 林涛、所有事件产生方 |

## 六 实施里程碑

建议以两周为一个迭代，总周期八周；若为课程项目或截止日期更短，可把每个迭代压缩为一周，但不要改变依赖顺序。

### 第 0 周 需求冻结与工程准备

- 全员确认车型字段、对比字段、配置规则、品牌视觉、地图供应商、AI 预算与留存策略。
- 林涛建立仓库骨架、环境与 CI。
- 六人共同评审 API 契约和数据库 ER 图。
- 周子涵建立验收用例与测试数据模板。

退出条件：本地一条命令启动 web、admin、api 和数据库；CI 通过；第一版 OpenAPI 可查看。

### 第 1 至 2 周 M1 车型和权限闭环

- 林涛：登录、角色、车型基础 API、上传和迁移。
- 唐轩：首页框架、车型列表和详情。
- 汤毅威：登录、CMS 框架、车型 CRUD 和审核流。
- 糜昊廷：AI 技术验证、流式接口 spike、评测集草案。
- 李昱彤：对比和选配的数据契约、参数标准化。
- 周子涵：E2E 骨架、车型发布到官网展示的主流程测试。

退出条件：管理员录入并发布车型，访客端可看到相同数据；权限矩阵通过测试。

### 第 3 至 4 周 M2 AI 和车型对比

- 糜昊廷完成 AI 对话、推荐校验、追问、错误处理和日志。
- 李昱彤完成对比篮子、对比页和差异高亮。

## 七 每周协作机制

### 固定节奏

- 周一：30 分钟迭代计划，只确认本周可验收结果。
- 每天：10 分钟同步阻塞，跨模块问题当天登记。
- 周三：接口和联调检查，禁止到周五才第一次联调。
- 周五：模块演示、缺陷复盘、下周范围确认。

### Pull Request 规则

- 一个分支只做一个任务，沿用 `feature/xxx`、`bugfix/xxx`。
- PR 必须说明需求编号、改动、验证步骤、截图或录屏、风险和回滚方式。
- 至少一名非作者评审；数据库、鉴权、AI、安全和计价变更需要指定责任人评审。
- PR 超过约 500 行有效业务改动时优先拆分，不把脚手架生成文件计算在内。
- 合并前必须同步最新 main 并通过所有自动门禁。

### 建议交叉评审

| 作者 | 首选评审人 | 评审重点 |
|---|---|---|
| 林涛 | 汤毅威或糜昊廷 | 权限、API 可用性、后端边界 |
| 唐轩 | 李昱彤 | 组件复用、状态和响应式 |
| 汤毅威 | 林涛 | 权限、数据校验、审核状态 |
| 糜昊廷 | 林涛和周子涵 | 数据真实性、安全、可测试性 |
| 李昱彤 | 唐轩和汤毅威 | 参数一致性、计价、跨页面状态 |
| 周子涵 | 林涛或唐轩 | 统计口径、地图抽象、E2E 稳定性 |

## 八 完成定义

一个任务只有同时满足以下条件才算完成：

- 对应用户故事和验收标准已关联。
- 正常流程与关键异常流程均有测试。
- 类型检查、lint、单元测试和相关 E2E 通过。
- API、字段、错误码或统计口径的变更已更新文档。
- 无真实密钥、账号或个人信息进入仓库。
- 已在测试环境由非作者验证。
- PR 已评审并合并，任务记录了演示或验收证据。

## 九 开工前必须确认的五项

## 十一 分工调整规则
